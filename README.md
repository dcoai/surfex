# Surfex

Surfex keeps code and its specification in sync by making the link between them
something the build checks, not something people have to remember. Your spec already
names the code it describes: `MyApp.Cart.add`, a struct, a constant. Surfex reads those
names from the spec's prose, reads your source without compiling it, and checks both
directions. Every name the spec cites must exist, and every public module and function
must be cited by the spec or deliberately excused. The result is a markdown **golden**
listing every item with a content hash of its definition and the spec sections that cite
it. CI regenerates it and byte-compares it with the committed copy, so any disagreement
between spec and code fails the build. This matters most when LLMs write a lot of the
code. An agent can change an implementation in seconds and leave the specification
behind, and prose gives no warning when that happens. With a gated trace, that drift
turns the build red, and the failure names the spec sections to revisit. The golden is
also a compact, always-current map of the system that an agent can read instead of the
whole codebase, and trust, because it cannot be out of date without the build failing.

## Installation

Add `surfex` to your dependencies in `mix.exs`. It is a build-time tool, so keep it out
of your runtime and your consumers' dependency trees:

```elixir
def deps do
  [
    {:surfex, "~> 0.2", only: [:dev, :test], runtime: false}
  ]
end
```

Surfex has no dependencies of its own and needs only the Elixir standard library.

## Usage

### Trace your spec against your code

A cart module, and the spec that describes it:

```elixir
# lib/my_app/cart.ex
defmodule MyApp.Cart do
  @moduledoc "A shopping cart."

  @doc "An empty cart."
  def new, do: []

  @doc "Adds `qty` of `item`."
  def add(cart, item, qty \\ 1), do: [{item, qty} | cart]

  @doc "The number of items in the cart."
  def total(cart), do: Enum.reduce(cart, 0, fn {_item, qty}, sum -> sum + qty end)
end
```

```markdown
# Carts

`MyApp.Cart` holds what a customer is buying. `MyApp.Cart.new/0` starts an empty one.

## Adding items

`MyApp.Cart.add` puts `qty` of an item in the cart, one by default.

## Totals

`MyApp.Cart.total/1` counts the items.
```

Tell Surfex where the spec is. `require_citation` makes the named sections cite code:

```elixir
# .surfex.exs
[
  sources: ["spec.md"],
  require_citation: ~r/^(Adding items|Totals)$/
]
```

```sh
mix surfex.goldens --write     # write SPEC_TRACE.md; commit it
mix surfex.goldens             # the CI gate
```

```markdown
# SPEC_TRACE.md
Every item the code declares, and the spec sections that cite it.
Generated by `mix surfex.goldens --write` · gate `spec-trace-drift` (HARD) — do not edit; a drift FAILS the gate.

**5 items** · cited 5 · expected-silent 0 · GAPS 0 · citations 4 · unresolved 0 · ambiguous 0

## Modules

| Item | Kind | Version | Cited by | Locus |
|---|---|---|---|---|
| `MyApp.Cart` | `:module` | `8e236378` | `spec — Carts` | `lib/my_app/cart.ex` |
## Functions

| Item | Kind | Version | Cited by | Locus |
|---|---|---|---|---|
| `MyApp.Cart.add/2` | `:function` | `35dbb372` | `spec — Adding items` | `lib/my_app/cart.ex` |
| `MyApp.Cart.add/3` | `:function` | `35dbb372` | `spec — Adding items` | `lib/my_app/cart.ex` |
| `MyApp.Cart.new/0` | `:function` | `8549a9d9` | `spec — Carts` | `lib/my_app/cart.ex` |
| `MyApp.Cart.total/1` | `:function` | `084ca327` | `spec — Totals` | `lib/my_app/cart.ex` |
```

`MyApp.Cart.add` without an arity cites every arity. The default argument makes
`add/2` and `add/3` one function, with one hash.

Now someone adds `clear/1` to the cart and, in the spec, promises a `discount/2` nobody
has written. `mix surfex.goldens` reports all of it in one run:

```
** (Mix) SPEC_TRACE.md: out of date.

Changed (the sections listed cite them — revisit each):
  MyApp.Cart → spec — Carts

Added (nothing in the spec covers them yet):
  MyApp.Cart.clear/1

Regenerate with `mix surfex.goldens --write` once the source is right.
GAP: `MyApp.Cart.clear/1` is neither cited by the spec nor excused by a class
unresolved: `MyApp.Cart.discount/2` at spec.md:11, Totals
```

Editing a function's body changes its hash, and the failure names the spec sections
citing it: the ones to reread. Moving a function, re-indenting it, or adding a comment
above it changes nothing.

### Excuse what the spec is deliberately silent about

Not all code belongs in a spec. Excuse it by **class**, with a reason the golden prints,
never item by item. A new helper then falls into its class, and a new entry point is
still a gap:

```elixir
# .surfex.exs
[
  sources: ["spec.md"],
  classes: [{"process plumbing", "GenServer callbacks; the spec describes the behaviour"}],
  rules: [%{class: "process plumbing", kinds: [:function], name: ~r/^(init|handle_\w+)\//}]
]
```

A row it excuses reads `— process plumbing` where a citation would be.

### Gate your own goldens alongside the trace

The part only your project can write is a scanner for its own surface: the endpoints a
router declares, the actions a model defines. Implement `Surfex.Surface`, list it in
`.surfex.exs`, and the same command gates it. Keep it where only dev and test compile it
(here `test/support`, with `elixirc_paths(:test)` including it), since Surfex is a
dev/test dependency:

```elixir
# test/support/modules_golden.ex
defmodule MyApp.Goldens.Modules do
  @moduledoc false
  @behaviour Surfex.Surface

  alias Surfex.{Golden, SourceScan}

  @impl true
  def spec(_opts) do
    rows =
      for file <- Path.wildcard("lib/**/*.ex"),
          node <- file |> File.read!() |> Code.string_to_quoted!() |> SourceScan.defmodules() do
        {:defmodule, _, [name, _]} = node

        %{
          "Module" => {:code, Macro.to_string(name)},
          "Functions" => "#{length(SourceScan.defs(node))}",
          "Version" => {:version, SourceScan.definition_hash(node)}
        }
      end

    %{
      name: "MODULES.md",
      purpose: "Every module in lib/, and how many public functions it has.",
      task: "surfex.goldens",
      gate: "modules-drift",
      hardness: :hard,
      columns: ["Module", "Functions", "Version"],
      stats: [Golden.stat("#{length(rows)} modules", [])],
      rows: rows
    }
  end
end
```

```elixir
# .surfex.exs
[
  goldens: [:trace, {"MODULES.md", MyApp.Goldens.Modules, []}],
  sources: ["spec.md"]
]
```

```yaml
# .gitlab-ci.yml
goldens:
  variables:
    MIX_ENV: test
  script:
    - mix surfex.goldens
```

## How it reads a spec

- **A code span is a citation when it names something.** `` `MyApp.Cart.total/1` ``
  cites that function, and `` `MyApp.Cart.add` `` cites every arity. A span shaped like
  your code's names that names nothing is a broken citation. Anything else in backticks
  is prose.
- **Every citation has one status:** resolved, ambiguous (never guessed), unresolved,
  external (real but outside the scanned tree), or a documented absence (a section that
  names something because the code lacks it).
- **Every item has one verdict:** cited, excused by a class, or GAP.
- It also reads code blocks, table columns you name (cells there are citations without
  backticks), sections declared to be *about* a structure (bare member names inside them
  resolve to it), and member paths like `header.ack.client_id`.

`spec.md` in this repository is the full specification, and Surfex traces it against its
own code in CI.

## What it gives you

| Module | What for |
|---|---|
| `Surfex.Golden` | renders any golden: typed cells, stats lines, grouped tables, identical bytes every time |
| `Surfex.SourceScan` | reads Elixir without compiling: modules, public definitions, content hashes |
| `Surfex.Scanner`, `Surfex.Scanner.Elixir` | the scanner contract, and the built-in one for Elixir |
| `Surfex.Cite`, `Surfex.Coverage`, `Surfex.Profile` | citations, verdicts, and the data that configures them |
| `Surfex.Trace` | a whole trace: analysis, failures, the golden, drift |
| `Surfex.Surface`, `Surfex.Goldens`, `Surfex.Gate` | project goldens, and gating all of them |
| `mix surfex.goldens`, `mix surfex.trace` | every golden, or the trace alone |

`Surfex.SourceScan.definition_hash/1` strips **all** AST metadata before hashing, so a
version is a function of a definition's structure, not its position. **A line number
reports movement; this hash reports change.** That is why two people editing different
items touch different rows, so goldens merge instead of conflicting.

## The rules it enforces for you

**Order-invariance.** A golden is invariant under the order of a row map's keys and of
the row list. A scanner that returned rows in a different order on a different run would
otherwise fail the gate with no change to the code, and a gate that fails for no reason
is a gate somebody switches off.

**No timestamps, no VCS data.** A golden is a stable function of source. A date makes it
drift against itself on a quiet day. Tests assert that dates never reach a golden,
because this is the rule most likely to be re-broken by someone adding a helpful
"generated at".

**Loud over silent.** A config key Surfex doesn't know, a spec glob that matches nothing,
a scan that finds nothing, or a `require_citation` that matches no heading all stop the
run before anything renders. A misconfigured gate must never render a golden that
passes.

## What it deliberately does not know

Surfex knows **one generic surface**, an Elixir project's public API (and the scanner
is pluggable, so a C header or a protocol description works too), and **one generic
relation**, citation. It does not know:

- **Your vocabulary.** Which kinds of item are your spec's subject matter, which classes
  of code it may stay silent about, and why: that is your profile, as data. It is printed
  in your golden, so reviewers see it.
- **Your other surfaces.** Finding a router's endpoints, a `TLA.Spec` action or a
  terminal escape sequence is a scanner's job, and a scanner belongs to the project whose
  vocabulary it reads. That is what `Surfex.Surface` is for.
- **Your evidence ladder.** `model_checked ▸ refinement_checked ▸ …` or
  `static_gate ▸ property ▸ unit_test ▸ NOTHING`: these differ per project. Surfex
  renders typed cells and never interprets them.

## The document's shape

1. **Header block**: three contiguous lines, `# <NAME>`, the one-line purpose, and a
   machine-parseable attribution naming the task, the gate, and whether it is HARD or
   ADVISORY. Free prose may follow.
2. **Stats lines**: `**<lead>** · <label> <n> · …`, built with `Surfex.Golden.stat/2` so
   the counts stay data and a report can read them back.
3. **Tables**: the first column is the catalogued item, and the last is conventionally
   `Locus`. Optional `## <heading>` grouping.

## Where it came from

The golden renderer was extracted from `agentronic`, where ten goldens use it in
production (`SPEC_COVERAGE.md`, `AUTHZ_SURFACE.md`, `NODE_INTERFACE.md`,
`WIRE_SURFACE.md` and others). The two-way trace generalises one that a protocol
specification project built to hold its spec to a C reference implementation. This
repository tests it against an invented protocol of its own.

`deps: []`, stdlib only. That's a policy, not a coincidence: every project that takes
Surfex as a dev/test dependency would inherit anything it depended on.
