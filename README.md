# Surfex

Surfex keeps a specification and LLM-generated code in sync.

Your spec already names the code it describes: `MyApp.Cart.add`, a struct, a constant.
Surfex reads those names from the spec, reads your source without compiling it, and
checks both directions: every name the spec cites must exist, and every public module and
function must be cited or deliberately excused. It records the result in a markdown
**golden**: each item, a hash of its definition, and the spec sections that cite it. CI
regenerates the golden and compares it with the committed copy, so when an agent changes
the code and leaves the spec behind, the build fails and names the sections to revisit.
The golden is also a compact, always-current map of the system that an agent can read
instead of the whole codebase.

## Installation

Surfex is a build-time tool with no dependencies of its own:

```elixir
def deps do
  [
    {:surfex, github: "dcoai/surfex", tag: "v0.2.8", only: [:dev, :test], runtime: false}
  ]
end
```

## A worked example

The code, and the spec that describes it:

```elixir
# lib/my_app/cart.ex
defmodule MyApp.Cart do
  @moduledoc "A shopping cart."

  @doc "An empty cart."
  def new, do: []

  @doc "Adds `qty` of `item`."
  def add(cart, item, qty \\ 1), do: [{item, qty} | cart]

  @doc "The number of items in the cart."
  def total(cart), do: Enum.reduce(cart, 0, fn {_item, qty}, sum -> sum + qty end)
end
```

```markdown
# Carts

`MyApp.Cart` holds what a customer is buying. `MyApp.Cart.new/0` starts an empty one.

## Adding items

`MyApp.Cart.add` puts `qty` of an item in the cart, one by default.

## Totals

`MyApp.Cart.total/1` counts the items.
```

Tell Surfex where the spec is. `require_citation` makes the named sections cite code:

```elixir
# .surfex.exs
[
  sources: ["spec.md"],
  require_citation: ~r/^(Adding items|Totals)$/
]
```

Run `mix surfex.goldens --write` and commit the result. `mix surfex.goldens` is the CI
check.

```markdown
# SPEC_TRACE.md
Every item the code declares, and the spec sections that cite it.
Generated by `mix surfex.goldens --write` · gate `spec-trace-drift` (HARD) — do not edit; a drift FAILS the gate.

**5 items** · cited 5 · expected-silent 0 · GAPS 0 · citations 4 · unresolved 0 · ambiguous 0

## Modules

| Item | Kind | Version | Cited by | Locus |
|---|---|---|---|---|
| `MyApp.Cart` | `:module` | `8e236378` | `spec — Carts` | `lib/my_app/cart.ex` |
## Functions

| Item | Kind | Version | Cited by | Locus |
|---|---|---|---|---|
| `MyApp.Cart.add/2` | `:function` | `d2a86a6f` | `spec — Adding items` | `lib/my_app/cart.ex` |
| `MyApp.Cart.add/3` | `:function` | `d2a86a6f` | `spec — Adding items` | `lib/my_app/cart.ex` |
| `MyApp.Cart.new/0` | `:function` | `a89bff62` | `spec — Carts` | `lib/my_app/cart.ex` |
| `MyApp.Cart.total/1` | `:function` | `8147851d` | `spec — Totals` | `lib/my_app/cart.ex` |
```

Citing `MyApp.Cart.add` without an arity covers both arities. Now someone adds `clear/1`
and the spec promises a `discount/2` nobody wrote. The check reports all of it at once:

```
** (Mix) SPEC_TRACE.md: out of date.

Changed (the sections listed cite them — revisit each):
  MyApp.Cart → spec — Carts

Added (nothing in the spec covers them yet):
  MyApp.Cart.clear/1

Regenerate with `mix surfex.goldens --write` once the source is right.
GAP: `MyApp.Cart.clear/1` is neither cited by the spec nor excused by a class
unresolved: `MyApp.Cart.discount/2` at spec.md:11, Totals
```

Editing a function's body changes its hash. Moving it, reformatting it or adding a
comment above it doesn't.

## Beyond the example

**Excuse code the spec is deliberately silent about** by class, with a reason the golden
prints. A new helper falls into its class; a new entry point is still a gap:

```elixir
# .surfex.exs
[
  sources: ["spec.md"],
  classes: [{"process plumbing", "GenServer callbacks; the spec describes the behaviour"}],
  rules: [%{class: "process plumbing", kinds: [:function], name: ~r/^(init|handle_\w+)\//}]
]
```

**Gate your own goldens** alongside the trace: a module implementing `Surfex.Surface`
returns a golden as data (the endpoints a router declares, say), and the same command
writes and checks it. Keep it in `test/support`, since Surfex is a dev/test dependency:

```elixir
# .surfex.exs
[
  goldens: [:trace, {"MODULES.md", MyApp.Goldens.Modules, []}],
  sources: ["spec.md"]
]
```

**Trace code that isn't Elixir** by implementing `Surfex.Scanner`: the rest of the trace is
language-agnostic.

## Reference

[`spec.md`](spec.md) is the full specification: how a spec is read (the citation
statuses, subject sections, table columns, member paths), every `.surfex.exs` key, and
the golden's format. Surfex traces it against its own code in CI, so it can't fall out
of date.

Goldens never contain dates or version-control data, render identically whatever order
their rows arrive in, and any misconfiguration fails loudly before anything is written.
